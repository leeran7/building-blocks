## The headline: the quality gates did not hold

The suite is green, CI is green, and both typechecks are clean — and that tells
us much less than it appears to. This is the most important result of the review,
because it is the reason the rest of the findings reached `main`.

### The lint gate passes without linting anything — *verified*

`app/` contains no ESLint config at all. `pnpm lint` runs `next lint`, which in a
non-TTY prints its interactive setup prompt and exits 0. The CI log for run
`33252114342` (commit `f76090a`) shows exactly that:

```
Lint  ? How would you like to configure ESLint?
Lint  ❯ Strict (recommended) / Base / Cancel
```

and the step reported **success**. Every commit on 29 August passed a lint gate
that linted zero files. Two `eslint-disable-next-line react-hooks/exhaustive-deps`
comments in `app/src/game/useClimb.ts` (lines 117, 191) suppress a rule that has
never executed — and one of them makes a claim that is false (see F-13).

### A quarter of the app suite never executes production code — *verified*

There are **185 source-text assertions** across five test files — `readFileSync`
plus `toContain` / `not.toMatch` against production *source text* rather than
behaviour. **77 of 298 app tests (26%) never execute a line of production code**,
and no test anywhere invokes an API route handler, though 326 lines of route code
changed on 29 August.

Three distinct ways this produced a false green:

**1. Empty-paren assertions are always vacuous.**

```19:22:app/tests/api/paidStacks.test.ts
    const src = readFileSync(resolve(__dirname, "../../app/b/[slug]/page.tsx"), "utf-8");
    expect(src).toContain("parseSeasonSlug");
    expect(src).not.toContain("getOrCreateActiveSeason()");
```

The file calls `getOrCreateActiveSeason(seasonSlug)` at `app/app/b/[slug]/page.tsx:56`,
so the literal with empty parens never appears. The test passes while the exact
bug it is named after is live in production. The same trap appears at
`paidStacks.test.ts:42` and `:80`. Line 30 of that file does it correctly, by
matching the bare identifier.

**2. A negative lookahead exempts the form it exists to forbid.**

`app/tests/api/webhook.test.ts:54` guards against a non-additive altitude write
with `/altitude:\s*metresAdded(?!\s*\})/`. Executing it against the dangerous
string proves the guard inverted:

```
dangerous form: "data: { altitude: metresAdded }"
webhook.test.ts regex  -> no match -> not.toMatch PASSES
checkout.test.ts regex -> match    -> not.toMatch FAILS  (correct)
```

The near-duplicate assertion at `app/tests/api/checkout.test.ts:152` lacks the
lookahead and would catch it. Where two files guard the same invariant at
different strengths, the weaker one silently defines the guarantee.

**3. A test re-implements production logic, and the copy has diverged.**

`app/src/__tests__/v2.test.ts:211-233` re-implements `estimateDaysUntilBuried`
under a comment claiming it "mirrors the production logic in
`app/api/dashboard/route.ts` exactly". It does not:

| | test copy | production (`dashboard/route.ts:44-60`) |
|---|---|---|
| AC-23 never-buried cap | absent | `if (altitude > G0 * MAX_GROWTH) return null` |
| rounding | `Math.round` | `Math.floor` ("AC-21 conservative") |
| constants | `process.env["ENGINE_G0"] ?? 10` | `DEFAULT_CONSTANTS` → `G0 = 0.65` |

`G0 * MAX_GROWTH = 0.65 × 8 = 5.2`, confirmed at `app/src/engine/constants.ts:43,45`.
Production therefore returns `null` for any altitude above 5.2, so two tests
assert the **inverse** of production behaviour and pass: `v2.test.ts:242-246`
expects `estimateDaysUntilBuried(1e6, 0) > 1000`, and `:259-267` expects the
result for altitude 100 to be non-null. Production returns `null` for both.
AC-23 has zero coverage.

## Critical findings

### Security and trust boundaries

**F-1 — The free-climb leaderboard accepts an unbounded client-supplied score, permanently.** *Verified.*

`app/app/api/climb/result/route.ts:58` bounds `peakY` only by `>= 0`. There is no
ceiling, no cross-check against `finishedTick` (which is parsed at `:52` and
stored but never used to validate), and no re-simulation from `seed`.
`app/src/db/climb.ts:44-47,83` then applies the value through `nextPeak`, which
is `Math.max` — **monotonic by design, so a poisoned value can never be lowered
again** without direct database surgery.

The route's own docstring at lines 11-13 states that ranked results "are
re-simulated server-side from seed + input log (AC-17); that path is separate".
No such path exists anywhere in `app/app/api`. Combined with F-2 (anti-cheat is
dead code), there is no server-side score validation at all. The leaderboard is
rendered on the landing page beside the paid stacks, so this is
reputation-adjacent even though the stack is labelled free.

Remediation, in order of strength: re-simulate from `seed` plus a submitted input
log; or at minimum reject any submission where `peakY` exceeds
`maxClimbSpeed × RAPID_CLIMB_MULT × finishedTick × TICK_DT` plus tolerance, and
require `finishedTick`.

**F-2 — `next` is pinned at `14.0.4`, which carries a critical middleware authorization-bypass CVE.**

CVE-2025-29927: a request carrying the `x-middleware-subrequest` header causes
Next to skip middleware entirely. `app/middleware.ts` is exactly the file this
diff expanded by 66 lines. The same version also carries CVE-2024-51479 (a second
authorization bypass), CVE-2024-34351 (SSRF in Server Actions), and cache
poisoning.

Blast radius is genuinely limited: the middleware guard is presence-only by
design (stated at `middleware.ts:8-9`) and real authorization lives in route
handlers via `requireAuth`, so this does not by itself expose another user's data.
It is still an unauthenticated, header-only, publicly documented bypass of a
control this diff expanded.

`pnpm audit` in `app/`: **61 vulnerabilities (2 critical, 22 high, 30 moderate,
7 low)**. `next` alone accounts for the critical and 15 of the 22 highs, so a
bump to ≥15.5.21 is the single highest-leverage action. `vitest` 1.x carries
CVE-2026-47429 (dev-only; requires the Vitest UI server). `orchestrator` has 12
findings, 3 high, all `undici` via `@cursor/sdk`, no criticals.

The exact pin means `pnpm update` will not move it.

**F-3 — The Stripe webhook credits altitude without checking `payment_status`.**

`app/app/api/webhook/stripe/route.ts:56-121` handles `checkout.session.completed`
and immediately credits from `amount_total`, never reading
`session.payment_status`. `checkout/route.ts:254` does not set
`payment_method_types`, so the enabled method set is controlled from the Stripe
Dashboard. If any delayed-notification method is enabled (ACH, SEPA debit,
Klarna, Bacs, OXXO), that event fires with `payment_status: "unpaid"` and the
block receives permanent, explicitly non-refundable altitude before funds settle.
There is no `checkout.session.async_payment_failed` handler.

**This is rated critical-if-configured and needs a Dashboard check that code
review cannot perform.** Fix regardless: gate the credit on
`payment_status === "paid"`, add an `async_payment_succeeded` handler, and
consider pinning `payment_method_types: ["card"]`.

**F-4 — Two webhook error paths permanently lose a captured payment.**

`webhook/stripe/route.ts:84` returns **400** when `getBlockById` is null. Stripe
treats 4xx as final and never retries, so the charge is captured and never
credited. Line 99 returns **500** for an unparseable stack, which Stripe *does*
retry — but the block's category is persistent, so every retry fails identically
until Stripe gives up. Both end in silent money loss with nothing beyond a
`console.error`.

### Correctness

**F-5 — The ghost tech season was not actually fixed.** *Verified.*

The change removed every `category = "tech"` default — the symptom — but left
`getOrCreateActiveSeason` on three public **read** paths:

| Call site | Path | Test guard |
|---|---|---|
| `app/app/api/tower/[category]/route.ts:59` | unauthenticated GET, polled every 10s by `TowerView` | none |
| `app/app/b/[slug]/page.tsx:56` | public record page render | vacuous (see above) |
| `app/app/api/internal/credit-view/route.ts:61` | runs *before* the bot/dedup/cap filters | none |
| `app/app/api/checkout/route.ts:210` | payment | legitimate |
| `app/app/api/webhook/stripe/route.ts:105` | payment | legitimate |

`parseSeasonSlug` still accepts `"tech"`, so viewing any legacy tech-category
block recreates the tech season — the ghost season resurrecting from a page view.
The sibling `app/app/api/tower/route.ts:6` documents "This GET does not create
seasons" and was correctly converted to `getAllActiveSeasons`; its dynamic
sibling does the opposite.

The result is worse than before the fix: instead of one ghost `tech` season, an
anonymous visitor walking the 74-slug list can mint **up to 75 ghost seasons**,
and they surface in `getAllActiveSeasons()`, which both `/api/tower` and
`/api/dashboard` read. That is also unauthenticated row-creation amplification.

Fix: read paths use a nullable `getActiveSeason`; confine `getOrCreateActiveSeason`
to the two authenticated write paths.

**F-6 — Per-stack `views_k` is credited through global, un-scoped Redis keys, so every stack's view count is wrong.**

`incrementSeasonViews(category)` now targets one of 74 season rows, but the gates
deciding *whether* to credit were never re-keyed:

```23:26:app/src/views/sessionDedup.ts
export function dedupKey(sessionId: string, bucket: number): string {
  return `dedup:${sessionId}:${bucket}`;
}
```

No category component. A visitor browsing five stacks in one 30-minute window
credits only the first; the other four are recorded as `session_duplicate`
(`app/src/views/pipeline.ts:93-97`). So `views_k` no longer means "qualified
views of this stack" — it means "sessions whose first stack visit this window
happened to be here". `views_k` is the sole input to `computeGround` (burial) and
`computeRate` (metres per dollar), so **burial timing and the price of altitude
are skewed across all 74 stacks**. The hourly global ceiling
(`app/src/views/globalCeiling.ts:45`) has the same problem: once tripped it
freezes crediting for every stack at once.

**F-7 — `/climb` is prerendered at build time and never revalidates.**

`app/app/climb/page.tsx:21` calls `topFreeClimbers(50)` and exports neither
`dynamic` nor `revalidate`; `next build` marks it `○ /climb` (static). The
leaderboard is frozen at build time forever. Worse, line 21 is
`topFreeClimbers(50).catch(() => [])`, and a build log shows
`prisma.climbRecord.findMany()` failing with "Can't reach database server" *while
the build succeeded* — so a CI build without DB reachability bakes in a
permanently empty leaderboard and nothing fails. This is the day's headline
feature. `app/app/page.tsx:28` gets it right with `export const revalidate = 60`.

All 12 route handlers are correctly dynamic; this bug class landed on a server
component instead.

**F-8 — Two live entries of the same power-up type break an invariant four call sites rely on.** *Verified.*

`app/src/game/simulation.ts:416` pushes a new `ActivePowerUp` on every pickup with
no check for a live entry of the same type. `activeEntry`
(`app/src/game/powerups.ts:469`) then returns the *first* match — the older orb.
Measured across the four zero-cooldown types:

```
rapid-climb:  entries=2  remainingTicks=269  dur=300
sprint-burst: entries=2  remainingTicks=149  dur=180
super-jump:   entries=2  remainingTicks=209  dur=240
double-jump:  entries=2  remainingTicks=329  dur=360  charges=2  banked=4
```

Three consequences. The HUD chip shows the older orb's countdown, so it hits
`0.0s` and disappears while the effect is still running. `PowerUpHud.tsx:49` keys
chips by `a.type`, so two live entries render two children with the same React
key. And for `double-jump` it is a real exploit: two orbs yield **4–5 successful
mid-air jumps while `doubleJumpChargesRemaining` reports 2**, because
`consumeCharge` (`powerups.ts:518-522`) decrements only the first entry and
`.find()` falls through to the second.

Not exotic: `pickType` (`powerups.ts:311`) only applies a ×0.22 penalty to a
repeat rather than forbidding one, and the cluster branch (`:258`) deliberately
places orbs 1–2 floors apart. A scan of 40 seeds over floors 1–150 found 62
same-type orb pairs within 3 floors. The only existing duplicate-pickup tests use
`time-slow` — the one type whose non-zero cooldown blocks the path.

Fix: on pickup, refresh the existing live entry's `startTick` rather than
appending. Keying the HUD by `${type}:${startTick}` only hides the symptom.

**F-9 — `/api/tower`'s `season` and `engine` blocks are derived from whichever block happens to be rank 1.**

`app/app/api/tower/route.ts:54-58` computes `engine.ground`, `engine.rate`,
`engine.growth` and `cost_of_rank1_usd` (`:82`) from `topV` — one stack's views —
while each block's `buried` flag correctly uses its own stack (`:61`). These
disagree by construction, and `TowerView.tsx:105-107` draws the ground line from
`engine.ground` while colouring rows from `buried`, so a block can render above
the ground line while flagged buried. Also `season.id: "none"` (`:92`) is a magic
string in an ID field.

Latent rather than visibly broken — both `TowerView` call sites pass an explicit
`pollUrl` and `app/layout.tsx:51` reads only `blocks[0]` — but the fields are
public and actively misleading. The response *shape* is unchanged, so no contract
test could catch it.

**F-10 — Season rollover is destructive and non-idempotent.**

`app/app/api/admin/season-rollover/route.ts:33` → `rolloverSeason`
(`app/src/db/seasons.ts:94-115`). Every POST deactivates the active season and
creates a replacement with `views_k = 0`. No idempotency key, no check that
`ends_at` has passed, no dry-run — so a retried or double-submitted request rolls
over twice and resets ground and pricing for the whole stack again.

Concurrency is *contained* (the partial unique index at
`0004_season_category/migration.sql:15` makes the losing transaction roll back)
but reported badly: it surfaces as a generic 500, so an operator cannot
distinguish a benign conflict from a real fault.

### Frontend

**F-11 — The canvas backing store is reallocated and cleared on every frame.** *Verified.*

```87:90:app/src/components/Game/ClimbCanvas.tsx
    const dpr = typeof window !== "undefined" ? window.devicePixelRatio || 1 : 1;
    canvas.width = width * dpr;
    canvas.height = height * dpr;
    ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
```

The effect's dependency array is `[state, width, height, reducedMotion, bottomInset]`
(`:330`) and `useClimb` produces a new `state` object every simulated tick
(`useClimb.ts:185`), so this runs ~60 times a second. Per the HTML spec,
assigning `canvas.width` resizes and clears the bitmap **even when the value is
unchanged**. This was tolerable when `MAX_WIDTH` was 560; the fullscreen change
raised it to 2560 (`useCanvasSize.ts:92`), so a desktop canvas is roughly
730×1300 CSS px — a ~15 MB bitmap at `devicePixelRatio` 2, thrown away and
re-zeroed 60 times a second. `dpr` is never clamped, so a 3× display triples it.

**F-12 — Tower geometry is recomputed from floor zero every frame, so the game gets slower the higher you climb.** *Verified.*

`floorHeight` and `floorIndexAt` (`app/src/game/towers.ts:109-125`) both walk
from floor 0, and each step calls `floorGapForFloor`, which builds a fresh
template string and a fresh `createRng` closure (`:138-143`) with no memoization.
`ClimbCanvas.tsx` calls them six-plus times per frame. Measured:

```
floorHeight scan of  400 floors:  30.6 ms
floorHeight scan of  800 floors: 123.2 ms   (2× floors → 4× time: quadratic)
floorHeight scan of 1600 floors: 480.7 ms
floorHeight(floor=1000) ×50:      18.8 ms
floorHeight(floor=5000) ×50:      94.2 ms   (linear per query)
```

This is the failure shape you least want in an endless climber: **frame cost
scales with the score.** It predates the diff, but the fullscreen change
increased the visible floor count. It is already visible in CI —
`powerups.test.ts` takes 3128 ms and `simulation.test.ts` 3661 ms while every
other suite is under 250 ms. There is no timing assertion anywhere in
`app/tests/**`, so a further regression would not be caught.

**F-13 — Power-up feedback refs are never reset between runs.**

`app/src/components/Game/usePowerUpFeedback.ts:41-42` holds `prevActiveKey` and
`prevPickupTick` for the lifetime of the hook, but `start()` builds a new match
with `tick = 0` and an empty `activePowerUps` (`useClimb.ts:203-208`). So if a
run ends while an effect is live — the common case, since power-ups are what let
you climb high enough to die — `prevActiveKey` still holds e.g. `"sprint-burst"`,
and the next Start fires an expire beep and announces "Sprint Burst ended." at
the top of a fresh run. Separately, `prevPickupTick` carries the previous run's
tick number across the reset, so a pickup landing on the same tick index is
silently dropped: no sound, no announcement, no live-region text.

**F-14 — The global keydown handler swallows Space and the arrow keys for the whole page.** *Verified.*

```121:127:app/src/game/useClimb.ts

    const down = (e: KeyboardEvent) => {
      if (isGameKey(e.key)) {
        e.preventDefault();
```

No phase guard, no target check, bound to `window`, active in `lobby`,

button has focus — "Start climb", "Climb again" (`ClimbScene.tsx:323-333`) and
the new mute toggle (`PowerUpHud.tsx:75-85`) cannot be activated with Space, the
standard activation key for a button. The arrow keys are likewise blocked, so a
keyboard user cannot scroll to the "How to play" card. Adding a keyboard-operable
button to a page that already has a global game key handler silently broke that
button.

**F-15 — The touch buttons are focusable but have no keyboard or AT activation path.**

`app/src/components/Game/TouchControls.tsx:95-128` renders real `<button>`
elements with `aria-label` and `aria-pressed` but wires only pointer events — no
`onKeyDown`, `onKeyUp` or `onClick`. Tab-plus-Enter, iOS Switch Control,
VoiceOver double-tap and TalkBack all reach the button, are told it is a
pressed-state control, and get nothing. Combined with F-14 (Space is
`preventDefault`ed anyway), these are advertised-but-inert controls.

**F-18 — The anti-cheat height sentinel would flag a legitimate super-jump.**

`app/src/game/antiCheat.ts:83-101`: `isHeightDeltaLegal` compares a *jump arc*
against the *ladder climb rate*, and `legalClimbSpeedMult` only widens the

| jump | consecutive illegal ticks | flagged at K=5 |
|---|---|---|
| plain ground jump | 4 | no — one tick from it |

The ceiling should be the sim's own vertical envelope:
`max(maxClimbSpeed × climbSpeedMult, jumpSpeed × SUPER_JUMP_MULT) × TICK_DT + tolerance`.

## Warnings

Grouped and abbreviated; each has a file:line in the agent handoffs.

**Data access.** Three unbounded `findMany` calls on hot paths: `getRankedBlocks`
has no `take` and no `select` and is called with no argument from the public
`/api/tower` (`blocks.ts:20-26`, `tower/route.ts:32`) — every visible block across
all 74 stacks, behind only `s-maxage=3`; `credit-view:71-75` then loops it with
one awaited round-trip per above-ground block (a single conditional `UPDATE`
would do); and `webhook:125-126` reads a whole stack to `findIndex` one row (an
indexed `count` would do). The scoped sibling route does it correctly with
`take: 100` plus an explicit `select`. The dashboard issues up to 74 concurrent
`findMany({ take: 500 })` against a PgBouncer-pooled connection
(`dashboard/route.ts:143-153`) and derives `rank` from position within that
window, so a block ranked 501st reports `rank: null`.

**Schema/migration drift.** `blocks_user_id_idx` and the partial unique
`season_one_active_per_category` exist in migration SQL but are **not declared**
in `schema.prisma`. The P2002 race guard in `getOrCreateActiveSeason` and the
rollover concurrency containment in F-10 rest entirely on that undeclared index; a
`prisma db push` would silently drop both protections.

**Unpaid blocks are created and publicly listed.** `checkout/route.ts:228-240`
inserts the `Block` row before the Stripe session, and nothing removes it if
checkout is abandoned; `blocks.ts:20-24` filters only on `hidden_at`. An
authenticated user can publish 30 attacker-chosen name/URL pairs per minute onto
public stack pages at altitude 0, permanently, for free. The name is sanitised and
the URL protocol-validated, so this bounds payload but not volume.

**CI injects production-grade secrets into a `pull_request` job.**
`.github/workflows/ci.yml:5-7,57-66` supplies `STRIPE_SECRET_KEY`,
`STRIPE_WEBHOOK_SECRET`, `INTERNAL_TOKEN`, `ADMIN_TOKEN` and Upstash credentials.
Fork PRs are safe (GitHub withholds secrets from fork-triggered `pull_request`,
and this is not `pull_request_target`), but any same-repo branch PR runs
`pnpm vitest` with those secrets in env, so a one-line test change exfiltrates
them; `pnpm install` lifecycle scripts run in the same scope. No `permissions:`
block; actions are tag-pinned rather than SHA-pinned.

**Internal-token hardening.** `credit-view/route.ts:32` uses a plain `!==` while
the project's own `requireAdmin.ts:40,53` does a constant-time comparison — the
good pattern existed and was not reused. It is also the only sensitive route with
no rate limit, so the token can be brute-forced at line rate.
Separately, `middleware.ts:125,147-153` sends `INTERNAL_TOKEN` to an origin
derived from `request.nextUrl.origin`. Not exploitable as configured
(`next.config.js` leaves `experimental.trustHostHeader` unset), but enabling that
flag — a common fix when deploying behind a proxy — silently converts it into an
unauthenticated token-exfiltration primitive.

**Web Audio.** The context is created lazily from a React effect scheduled off a
rAF `setState` — not a gesture handler — so the first cue is likely silent on iOS
(`powerUpAudio.ts:164-184`). The mute toggle, the clearest audio-intent gesture
on the page, deliberately no-ops when no context exists (`:102-111`), so it does
not unlock either. And `playNote` has no `try/catch` (`:135-162`) while
`ensureContext` does, so an `InvalidStateError` from an interrupted iOS context
propagates out of a `useEffect` and unmounts the whole game.

**Per-frame React work.** The sim state is cloned every tick and passed through
React state, making every consumer a 60 fps component: `usePowerUpFeedback` reruns
a `filter`/`map`/`sort`/`join` `useMemo` and its effect 60 times a second
(`:60-98`), and `PowerUpHud` regenerates an inline `linear-gradient` string every
frame (`:52-60`), forcing a style recalc and repaint alongside the canvas draw.
The canvas draws in `useEffect`, which runs *after* paint, adding a frame of
input latency and an extra composite.

**Unbounded cache.** `powerups.ts:269`'s `spawnScheduleCache` is a module-level
`Map` with no eviction. It was safe while keyed by a stable `solo-${slug}` seed;
`newRunSeed()` now mints a fresh seed per mount and per Start, so every run adds a
permanent entry whose array grows with altitude.

**Accessibility.** `text-muted` (`#74707e`) on void (`#0a0a0c`) is 4.11:1, below
the 4.5:1 AA minimum, and is used for 10–11px body copy in the HUD empty state
and the whole lobby controls guide — even though `ClimbCanvas.tsx:42-43` carries a
comment rejecting that exact colour for that exact reason. The mute button is a
~28px target inside a strip whose fixed `h-[46px]` caps it below 44px. An
`aria-live` announcement built from a constant string does not re-announce when
the same power-up is grabbed twice. `drawPickupBurst` and the pickup flash banner
ignore `prefers-reduced-motion` while the rest of the file honours it.

**Documented invariants that contradict the code.** `powerups.ts:18-19` states a
"one slot… hoarding is impossible" rule; production stacks all five types
simultaneously (2.625× combined multiplier) and `powerups.test.ts:236` asserts
stacking is correct. The doc is stale, and its "hoarding is impossible" premise is
load-bearing for the endless-run argument at `:27-37` — 4 banked double-jump
charges (F-8) is exactly hoarding. `tower/[category]/route.ts:7-9` still documents
a six-value Category enum it now 404s.

**Smaller items.** `checkout/route.ts:179-181` initialises branch-assigned locals
to `""`, disabling definite-assignment checking so a branch that forgets
`redirectSlug` yields `success_url: /b/?payment=success` with no compile error.
`amount_usd` has no upper bound (`z.number().positive()` admits `1e308`), turning
client input into a 500. `orchestrator/src/types.ts:220` decides handoff freshness
by lexicographic string comparison of ISO timestamps. `REQUIRED_TEAM`,
`REQUIRED_SEQUENCE`, `HANDOFF_STATUSES` and `PRIMARY_PIPELINE` — the loop's
enforcement mechanism — are exported as mutable arrays. `useClimb.ts:78` rebuilds
`cfg` every render while the rAF loop captures the first one, and the
`exhaustive-deps` suppression justifying it makes a false stability claim. Client
IP and Firebase UID are logged (`checkout:154`, `dashboard:218`). Two package
managers drive `orchestrator/` (`yarn` in CI and `test:orchestrator`, `pnpm` in
`yarn loop`) against a single `yarn.lock`.

## What is genuinely good

Not padding — this is calibration, and several of these are the model the rest
should copy.

**The lava retune is coherent, and provably so.** Despite four sequential retunes
in one day (`579620e`, `df3d3f5`, `b446bf1`, `c6d1346`), the final state is
self-consistent: `hazardHeightAt(200s)` matches a 300 Hz numerical integral of
`hazardSpeedFracAt` at `1877.633` vs `1877.633`; the curve is monotonically
non-decreasing across 0–400 s at 10 ms resolution; `hazardMeanSpeedFrac()` is
`1.1538`, matching the arithmetic in the `DEFAULT_HAZARD_CONFIG` comment; and the
run-must-end bound with perfect time-slow uptime lands at `1.0095`, above 1
exactly as claimed. It survived four retunes **because** the tests assert the
derived invariants rather than the constants.

**`app/tests/game/hazard.test.ts` is the best test file in the repo.** 13 tests,
13 ms, every one able to fail for a real reason: a monotonicity sweep over 200 s,
a *hostile-config* guard proving `stumbleSpeedFrac: -1` still cannot lower the
lava, a closed-form cross-check against the smooth integral, and the endless-run
invariant pinned to a named constant. This is the shape to copy.

**The revert was clean.** `5207759` left no orphaned unified-action control and no
dead props; `TouchControls` is back to a coherent four-button row with
`TOUCH_CONTROLS_INSET` correctly equal to `min-h-[92px] + p-2 × 2`. And `f76090a`
fully removed what `23d70c0` added — zero grep hits for `billboard`, `paidBlock`,
`hangingSign`, or the orphaned `roundRect` helper.

**Paid-stacks hardening is real.** The `parsePaidStackSlug` / `parseSeasonSlug`
split correctly separates "new money must name a real stack" from "a legacy block
may top up its existing season"; the webhook now derives the season from the
block row rather than client-controlled Stripe metadata; and the `Object.hasOwn`
conversions close genuine prototype-key holes. Replacing a permissive
default-to-`"tech"` with an allow-list parser that returns `null` eliminated a
whole bug class — that is the right instinct, and F-5 is a failure to finish it,
not a failure of the approach.

**No injection and no IDOR.** All raw SQL uses Prisma tagged templates. There is
no `dangerouslySetInnerHTML` anywhere under `app/`. `dashboard/route.ts:85` scopes
to `decoded.uid`. `safeRedirect.ts` correctly blocks `//`, `/\` and control
characters. SSRF is unreachable — no server-side fetch of a user-supplied URL
exists. Webhook double-credit is genuinely impossible: `stripe_session_id` is
`@unique` and `applyPaymentTransaction` is atomic, so a racing duplicate rolls
back.

**The orchestrator core does what `CLAUDE.md` claims.** `clampNextStage` genuinely
ignores requested skips outside `OPTIONAL_AFTER`; `teamMissing` genuinely blocks
completion when a required member was never dispatched; `withCriticalRevision`
genuinely converts a `success` handoff carrying critical findings into
`needs_revision` clamped to a backward target. No unhandled rejections, no shared
state mutation. `team.test.ts` and `stages.test.ts` are behavioural and
adversarial — the strongest tests added that day.

**RNG determinism holds.** Cold random-access `powerUpForFloor` on scattered
floors is byte-identical to the same calls after a warm sequential walk, so
`spawnScheduleCache` is a pure memo that does not perturb output. Power-up
placement respects floor geometry: across 5 seeds × 120 floors, 0 of 172 orbs sit
over a jump gap.

**Frontend hygiene is consistently right where it is easy to get wrong.**
Hydration and SSR safety are clean throughout — every file carries `"use client"`,
no module-level code touches `window`/`document`/`AudioContext`, and every
device-dependent hook starts from a server-safe value. Unmount cleanup is correct
everywhere (rAF cancellation, listener removal, observer teardown,
`audio.dispose()`). Oscillator nodes disconnect on `onended`, so there is no
per-pickup node accumulation. Touch and canvas input layering is not in conflict.

## Recommended fix order

Ordered by leverage. The first three are prerequisites: while the gates are
green-but-blind, no other fix can be trusted.

1. **Make the lint gate real** — add an ESLint config with `react-hooks` rules
   and `--max-warnings=0`, and prove it fails on a deliberately bad file. Expect
   this to surface a backlog; land the config with a baseline rather than fixing
   everything at once.
2. **Delete or rewrite the 185 source-grep assertions.** Priority: the three
   inverted/vacuous ones (`paidStacks.test.ts:21`, `webhook.test.ts:54`,
   `v2.test.ts:211-267`) before anything else, since those actively assert false
   things. Replace `tower.test.ts` wholesale with one response-shape contract test
   that invokes the handler.
3. **Bump `next` to ≥15.5.21** — clears the critical CVE and 15 of 22 highs — and
   add `pnpm audit --audit-level=high` as a CI gate.
4. **Close the score trust boundary** (F-1): bound `peakY` server-side against
   `finishedTick`, and either wire `antiCheat.ts` into the request path or delete
   it and stop citing AC-15/16/17/18 as covered.
5. **Finish the ghost-season fix** (F-5): nullable getter on all read paths;
   `getOrCreateActiveSeason` only on authenticated writes; a test asserting
   `season.create` is never called on any GET.
6. **Re-key the view-dedup and ceiling keys per category** (F-6) — every stack's
   `views_k`, and therefore burial and pricing, is currently wrong.
7. **Gate the Stripe credit on `payment_status === "paid"`** (F-3), and check the
   Dashboard's enabled payment methods. Convert the two money-losing webhook
   branches (F-4) to a dead-letter row plus 200.
8. **Add `export const revalidate` to `/climb`** (F-7) and fail the build when a
   prerendered DB read throws.
9. **Enforce one live entry per power-up type** (F-8) — refresh in place on
   pickup. Resolve the one-slot-vs-stacking doc contradiction first, since the
   fix differs.
10. **Fix the three per-frame faults** (F-11, F-12, F-13): guard the
    `canvas.width` assignment, memoize the cumulative floor-height prefix, reset
    the feedback refs on match change.
11. **Scope the global keydown handler** (F-14) and give the touch buttons a
    keyboard path or remove them from the tab order (F-15).
12. **Un-ignore the learnings ledger** (F-16) and either implement the three retro
